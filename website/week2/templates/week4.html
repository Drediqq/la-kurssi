Commands used

    Rsyncs .tar to server B
  • rsync -az -e "ssh -i "$SSH_KEY" -o BatchMode=yes" "${BACKUP_DIR}/${TAR_NAME}" "${REMOTE_USER}@${REMOTE_HOST}:${REMOTE_BACKUP_DIR}/"

    • Checks replication health on Server B to inspect Slave_IO_Running, Slave_SQL_Running, and lag. On Server A, you could check replications binary logging, with different command (obviously).
  • docker exec -e MYSQL_PWD="$DB_PASS" "$CONTAINER_NAME" mariadb -u"$DB_USER" -e "SHOW SLAVE STATUS\G" 2>&1 || true

    • Database backup. Quickly so nobody notices.
  • mariadb-dump --single-transaction --quick -u root -p"$MYSQL_ROOT_PASSWORD" "$MYSQL_DATABASE" > "$BACKUP_DIR/$BACKUP_FILE"

Storage and backups

Web root (Server A and Server B)

Served files live under /var/www/html


Backup staging and archives (Server A)

Backups are staged in /tmp/backups/lakurssi_TIMESTAMP and archived in /var/backups outside public directories so archives can't be downloaded


Remote backups on Server B: Hourly

rsync transfers place backups via ssh in a dedicated backup directory on Server B outside /var/www/html, protected with restrictive permissions.


Monitoring stats output:

replica_report.sh writes replica_status.txt and replica_lag.txt to /var/www/html/lakurssi/week2/templates/stats using temporary files (.tmp.$$) moved into place with 0644 so the web app never reads half-written output.

Linux users and ownership

Cron and automation scripts

Backup and replication monitoring scripts such as /usr/local/bin/replica_report.sh are owned and executed by via roots cron so it can manage docker containers, backup directories, and priviledged paths


Credentials and configs

env files holding database credentials which are restricted with 0600 and owned by root, those are also excluded from git so passwords and keys are never exposed to unprivileged users or the repo.


Web and backup isolation:

Keeping backup archives and SQL dumps out of /var/www/html prevents direct web exposure, while read-only permissions (0644) on generated status files allow the web server to read status strings without write access to scripts or configs.

Database users and privileges

Both servers have their own user for week2 app, but Server A database also has server B:s user as replication user. In both sites week2 still works, except Server B/week2 doesn't update the count to serverB/week4

Replication user can only SELECT from serverA:s database, nothing else.

Server Bs user also has replication slave monitor attribute to show the statistic for the table above.
