Documentation

Description of the request path (browser → Nginx → application → model / database)

  • User requests /week5/
  • Nginx matches the /week5/ location and proxies to Gunicorn/Flask
  • Flask renders the page and handles chat/API requests
  • Flask reads/writes conversation history in mariadb and sends prompts to ollama to generate a reply
  • Ollama returns generated response back through flask and nginx to the browser

Description of the pipeline

Pull requests: Runs the test job (ruff check ., pytest, and bash -n scripts/*.sh) to catch lint, test, or shell syntax issues early without deploying.

Push to main: Runs the test job first and once passing, the deploy job runs (serialized with concurrency so two deploys do not overlap). It syncs ./chatapp/ via rsync to /opt/chatapp/app/, runs scripts/deploy.sh to update the virtualenv, apply deploy/sql/schema.sql, validate and reload/restart Nginx with snippets/chatapp.conf, restart chatapp.service, and verify /health over the socket returns the new commit SHA.

Deployment verification: The workflow runs a public smoke test against /week5/health checking the exact commit SHA, /week5/ checking for id="chat-form", and week5.js.

Linux users, database users, file ownership and permissions, and where secrets are stored

Linux users
Chatapp user: The web application runs as a dedicated non-login system user with nologin through systemd.
Deploy user: Deployment connects over SSH using a standard login user with sudo access using a dedicated deploy key.

Database users
chatapp db user: A dedicated mariadb user has only privileges needed on the chatapp database.

File ownership and permissions
Application files are owned by deploy user and chatapp user with read/execute permissions so chatapp user can run the app without write access to code, and the environment file is restricted to root:chatapp with mode 0640.

Where secrets are stored:
CI/CD credentials are stored in github actions secrets, while runtime configuration like database password is stored on the server in env file which is readable only by root and the service user. No secrets or environment files are committed to git.

how you added /viikko5/ to Nginx without affecting other sites or pages

Rather than using a separate listening port or public IP for the web path, the existing Nginx site configuration was kept intact and extended with a new location for /week5/ block. Requests under week5/ are proxied to the Week 5 application's own localhost port or Unix after checking ss -ltnp and systemctl list-units to avoid conflicting ports. Deployment also checks syntax and conflicts with nginx -t
